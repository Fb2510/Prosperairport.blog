代理下载一跑就卡，软路由忙不过来了吗？

阿旺2026-11-05— 次阅读
软路由与排障

代理下载一开始就卡，可以先观察软路由在下载时是否持续忙碌。单凭“CPU 占用高”或一次测速，不能认定设备性能不足；更有用的是把卡顿、处理器状态和暂停下载后的变化放在一起看。

本文适用于运行 OpenWrt、由路由器承担代理转发的家庭场景。CPU 就是处理器，负责执行程序。如果代理实际运行在电脑或手机上，应先观察那台设备，路由器上的数字不能代替它。

先固定条件，别一边测一边换节点

选一台设备、一个确定经过代理的下载任务，临时固定当前节点。先暂停自己开启的其他大文件下载、云盘同步和测速，保持连接方式不变；能接网线时，可用有线连接减少 Wi-Fi 波动。

这一步是为了让变化容易比较。节点、下载来源、连接方式同时变了，速度恢复也很难知道是哪一步起作用。只需短时间重现日常问题，不必连续跑满流量。

在卡顿发生时，看一会儿 CPU

以下操作只适用于你已能通过 SSH 登录自己软路由的情况。SSH 是远程打开路由器命令行的方式；不熟悉登录操作时，可以先使用固件已有的 CPU 监控页面，找不到就向维护者确认，不必临时开启远程访问。

若固件带有 BusyBox 的 top 工具，在路由器命令行输入：

top -d 1

它会约每秒刷新一次进程状态。观察完成后按 q，或按 Ctrl+C 退出查看。这里退出的是监控工具，路由器的代理服务仍会继续运行。定制固件可能裁剪功能；提示命令或参数不支持时，先查该固件说明。

上述刷新参数和退出按键可见 BusyBox 的 top 项目实现与用法说明（2026 年 11 月 5 日核对）。

刚打开时先等几次刷新，再重点观察两处：

  • CPU 行的 idle：表示空闲时间的比例。持续很低时，说明对应统计范围内空闲较少；还要结合各项状态和实际卡顿判断。
  • 进程列表的 CPU 列：看看哪些运行中的程序在下载时明显变忙。进程可以理解为正在运行的程序，名称因代理插件而异，先核对名称，不要把排在前面的程序直接当成代理。

Load average 也可能出现在屏幕上，它不是 CPU 占用百分比，不要把其中的数字直接当作“用了百分之几”。

总占用不高，还要留意单个核心

多核处理器像有几名工人一起工作，整体平均值可能掩盖其中一名特别忙的情况。若你的 top 支持，按数字 1 可切换每个逻辑 CPU 的显示；出现 CPU0、CPU1 等行后，分别观察。没有这个功能时，不要凭整体数字排除处理能力方面的问题。

Linux 的 CPU 统计区分总体和每个逻辑 CPU，idle 是其中的空闲时间项，见 Linux 内核的 /proc/stat 说明（2026 年 11 月 5 日核对）。这也是观察多核设备时需要区分统计范围的原因。

做一次“下载—暂停”的对照

保持前面的节点和连接方式不变，按顺序观察：

  1. 下载前：看十几秒，记下平时 CPU 是否已经很忙。
  2. 开始下载：重现卡顿，同时记录大致速度、各 CPU 的空闲情况，以及明显变忙的进程。
  3. 暂停下载：继续观察十几秒，看 CPU 状态和日常打开网页的体验是否一起恢复。条件允许时，再重复一次确认。

下面是判断思路，并非本站实测结果：

观察到的现象 可以怎样继续查
下载时某个 CPU 持续很忙，暂停后占用和卡顿都明显回落 把软路由处理压力列为重点怀疑项，核对忙碌进程属于哪个组件
卡顿时各 CPU 仍有明显空闲 继续排查无线连接、节点和下载来源；这次观察尚未显示持续的 CPU 忙碌
没下载时也持续忙碌 先查是否有自己启动的同步、备份或其他后台任务

这些现象只能缩小范围。下载暂停后恢复，也可能与带宽不再被占满有关，不能单凭这一项证明 CPU 就是原因；短时间采样同样可能漏掉瞬间的忙碌。

接下来改一件事，再观察

若发现自己开启的后台任务占用明显，先用它原有的暂停功能停一下，再用同样条件比较。不要直接结束不认识的系统进程。

如果可疑的是代理组件，记录软路由型号、固件与插件版本、出现问题的时间，以及下载前后的变化，交给对应项目或维护者核对。截图发出前遮住订阅地址、令牌和账号信息。

这一步先把证据收齐，不需要为了试速度关闭防火墙、套用来历不明的“加速脚本”。是否需要换设备，要看你的实际使用量、持续可重复的观察和组件支持情况；不存在一个适用于所有软路由的“占用超过多少就该买新机”的标准。

资料核对日期：2026 年 11 月 5 日。本文提供观察方法，未进行具体设备或机场线路的性能测试。
